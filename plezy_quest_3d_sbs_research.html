● Research report — plezy-quest

Making Quest playback 3D:
what "SBS toggle" actually requires

You asked for a 3D/SBS toggle behind the dead fullscreen button, with a strength control. The UI half of that is a half-day change. The 3D half runs into a hard platform wall this fork has deliberately stayed on the right side of since day one — this report lays out exactly why, what a real fix costs, and the path that's actually worth building.

⚠

THE ONE THING TO READ FIRST

A GLSL shader that packs frames into side-by-side pixels will not look 3D on Quest. Plezy-quest is deliberately a flat 2D Android panel (no Spatial SDK, no VR intent — see QUEST_BUILD.md). Horizon composites that panel once and shows the identical image to both eyes. An SBS-packed frame on a flat panel just looks like a squashed double image, not depth. Real per-eye stereo on Quest requires Horizon's Spatial SDK stereo panel mode, which is a different, larger architecture — and a sibling project in your own memory already tried it and ripped it back out. Full story below.

1 Current state — the button you're replacing

Grounded directly in the current tree, not assumptions. The fullscreen affordance is real, wired, and dead in exactly the way you described.

Where it lives

The button is built in TrackChapterControls and rendered wherever the shared control row appears (desktop chrome and — via TvDetection counting Quest's absent touchscreen as a TV signal — the branch Quest actually renders through). Icon/label/handler are ordinary fields on an immutable TrackControlsState snapshot, the same shape used for the working zoom and box-fit buttons next to it.

Button itself — Symbols.fullscreen_rounded / fullscreen_exit_rounded, gated by a local isDesktop flag, onPressed: state.onToggleFullscreen.
lib/widgets/video_controls/parts/visibility.dart:189-192
The actual handler: if (!PlatformDetector.isDesktopOS()) return; — a hard early-exit for every non-Windows/macOS/Linux target. This is the dead no-op. isDesktopOS() checks the underlying OS, not device form factor, so Android/Quest can never pass it.

isDesktop(context) (UI-layout gate, !isMobile(context)) vs. isDesktopOS() (OS-capability gate, Windows/macOS/Linux only) are two different checks with the same name-shape — the button's visibility and its handler read different ones, which is exactly how a visible-but-inert button happens.
lib/widgets/video_controls/models/track_controls_state.dart:38,46

lib/widgets/video_controls/parts/track_controls.dart:155-210

The menu pattern you'd reuse

VideoSettingsSheet (lib/widgets/video_controls/sheets/video_settings_sheet.dart) is already a multi-view bottom sheet driven by a _SettingsView enum — zoom, playback speed, shader preset, DV conversion, HDR tone mapping all live here as sibling views, not separate toolbar buttons. _buildZoomView() (line 1026, a plain preset list) and the existing _SettingsToggleItem component (lines 157-242, a Pref<bool>-bound switch tile with revert-on-write-failure) are the direct templates for a new Mode + Strength view — no new sheet infrastructure needed, just a new enum case and a _buildThreeDView().

Where the setting would persist

ScopedPlayerPrefs.boxFitMode (lib/services/scoped_player_prefs.dart:57-62) is the exact template: a Pref<T> in SettingsService, an EnumPref<PlayerSettingScope> controlling off/global/library/title persistence, resolved through ScopedPlayerPrefs.resolve(). A 3D mode is a good candidate for per-title scope by default — a nature documentary and a screen-recording want very different defaults, and that scoping already exists as a first-class option.

2 Why a shader alone doesn't produce 3D

The mechanism you'd reach for — mpv's existing GLSL shader chain — is real, working, and exactly wired for this. It's also aimed at the wrong layer of the stack.

Horizon composites the Activity's window once and shows it to both eyes identically. An SBS-packed frame just renders as a visibly squashed side-by-side image — both eyes see both halves. No parallax, no depth, arguably worse than the flat original.

The compositor itself is told the surface is stereo-packed and splits it per eye. This split only exists on a panel registered through the Meta Spatial SDK — a plain Android SurfaceView, which is what Quest playback uses today, has no such mode.

Confirmed against your actual rendering pipeline

Quest video today: MpvPlayerCore.kt writes decoded frames to a plain SurfaceView in a normal FrameLayout — either directly (vo=mediacodec, hardware plane, no GPU pass) or through GLES (vo=gpu) whenever mpv's glsl-shaders property is non-empty. GpuVoPolicy.kt already auto-switches the session onto the GPU path the instant a shader is appended (REASON_SHADERS) — so the plumbing to run a custom GLSL pass on every frame is live and proven (it's how ArtCNN/NVScaler/Anime4K upscaling already ships). But that GPU pass renders into the same flat SurfaceView. Nothing downstream of it knows the output is stereo-packed. android/quest/src/main/AndroidManifest.xml explicitly omits com.oculus.intent.category.VR and headtracking features — by design, confirmed in QUEST_BUILD.md lines 1-6 and the manifest's own comments — which is precisely what keeps Horizon from ever offering a stereo panel mode to this app.

3 This isn't hypothetical — a sibling project already hit this wall

Holoplex (a related Quest media client in project memory) built the Spatial SDK immersive path first, then tore it out. The failure modes are on record and worth internalizing before scoping this.

What Holoplex tried and reverted (2026-08-26 pivot)

Holoplex ran as AppSystemActivity (Meta XR's immersive host) with ComposeViewPanelRegistration, IsdkGrabbable/IsdkPanelResize for native grab/move/scale, and — directly relevant here — VideoSurfacePanelRegistration for direct-to-surface media playback. It was deleted wholesale. Recorded reasons:

SymptomRoot cause
System keyboard (incl. dictation mic) never rendered over the panelSpatial panels live on virtual displays 41/43; the keyboardv2 IME only binds to display 0
On-device speech recognition errored instantlySpeechRecognizer models require a download Horizon's immersive sandbox didn't resolve
Panels intermittently loaded upside-downUnresolved Spatial SDK panel-orientation bug, not tied to any one code path
BackHandler crashed app-wideAppSystemActivity isn't a ComponentActivity, so Compose had no OnBackPressedDispatcherOwner — needed a hand-rolled provider to work around it

Holoplex's own durable-memory verdict: "for a fundamentally 2D browsing/media app, use a standard launcher activity." Plezy-quest already made that call from the start — this is independent confirmation it was the right one for the app as a whole.

Why this doesn't kill the idea — it scopes it

Holoplex's regressions came from making the entire app immersive — browsing, search, text entry, the works — live on Spatial SDK panels permanently. The keyboard and speech-recognition failures specifically hit UI you'd only need while typingonly for the seconds the user has 3D mode turned on during playback sidesteps most of that failure list by construction. The one item that doesn't obviously go away is the upside-down-panel bug — that's a platform-level Spatial SDK defect, not an artifact of Holoplex's specific screen graph, and it needs to be re-validated early on real hardware before betting the feature on it.

4 The actual technical shape of a working feature

Two independent problems hide inside "make it 3D": (a) getting Horizon to render a stereo-packed frame per-eye at all, and (b) producing a stereo-packed frame from 2D source material that was never shot in 3D. Neither is optional; source content in a Plex/Jellyfin library is overwhelmingly flat 2D.

REJECT

A · Flat-panel SBS shader only

Add an SBS/depth GLSL shader to ShaderService, ship it as a new ShaderPresetType, done in days.

  • Uses infrastructure that already exists and already works
  • Produces zero stereo depth on-device — see §2
  • Would ship a feature that visibly does nothing but squash the image
RECOMMENDED

B · Immersive "3D Theater" side-mode

A second, short-lived Activity/module (parallel to android/quest) that adopts the Spatial SDK only for this one surface, entered on toggle and exited back to the flat panel on close.

  • Main app, browsing, keyboard, snap points: completely untouched
  • ReadableVideoSurfacePanelRegistration accepts a plain Android Surface — mpv's existing decode path plugs straight in, no ExoPlayer migration needed
  • MediaPanelRenderOptions.stereoMode gives real per-eye split for content already mastered in 3D, free of any depth conversion
  • Real, scoped engineering effort — new Gradle module, playback handoff, lifecycle testing
N/A HERE

C · mpv --vf=stereo3d anaglyph

mpv's built-in filter can convert SBS/OU sources to red-cyan anaglyph 3D — a real, zero-architecture-risk option.

  • Works today on the flat panel with no Spatial SDK at all
  • Needs physical red-cyan glasses — meaningless inside a headset that already has stereo optics per eye
  • Worth knowing about for the Fire TV build, irrelevant to Quest

5 Where the "3D" pixels come from

Two very different content cases need two very different answers, and conflating them is the most common way this kind of feature disappoints.

SourceApproachEffortQuality
Already-3D movies (SBS/HSBS/OU masters, common for Plex "3D" tagged libraries) No conversion at all — just set stereoMode to match the file's real packing and let the panel split it per-eye Low Real stereo
Ordinary flat 2D (the overwhelming majority of any Plex/Jellyfin library) Synthesize a depth map, then displace pixels per-eye by depth × strength before packing SBS High Approximate

Depth-map generation for the 2D case — the part nobody ships casually

mpv has no built-in monocular depth estimation, and there's no real prior art for doing it live inside a GLSL //!HOOK shader — the community consensus (confirmed via current research into tools like VisionDepth3D / IW3 / Owl3D) is that real depth conversion runs an AI model (MiDaS / Depth Anything V2) as a separate offline pass, not a live player-side shader. Two tiers worth knowing apart:

Heuristic pseudo-depth (GLSL only)On-device ML depth (Depth-Anything-class model)
HowFake a depth cue from image statistics already visible to a shader — blur amount, vertical position, edge density, luminance gradient — then shift pixels by that proxy × strengthRun a small monocular depth network per frame (or every Nth frame with temporal smoothing) via NNAPI/GPU delegate, feed the depth texture into the same displacement shader
Fits existing infra?Yes — same ShaderService.applyPreset() path as ArtCNN/NVScaler today; "strength" is a genuine uniform/regenerated-shader parameter, same trick ambient_lighting_service.dart already uses for a runtime-generated shaderNo — needs a new native inference pipeline (model conversion + quantization + NNAPI or GPU delegate integration) that nothing in this codebase does today; XR2 Gen2's mobile budget makes full-res, full-framerate inference a real constraint, likely forcing reduced resolution/framerate or aggressive temporal caching
QualityCommunity-documented as "cardboard cutout" — flat depth planes, comfortable but not convincing, exactly why serious 2D-to-3D tools moved away from live heuristics years agoMeaningfully better, genuinely scene-aware depth; the actual bar every dedicated 2D-to-3D converter targets
ScopeDays, once Path B's stereo panel existsIts own multi-week project — treat as a distinct follow-on, not part of a v1

Recommended sequencing: ship real-3D-passthrough + the heuristic shader together as v1 (both ride on the same stereo-panel plumbing and the same ShaderService mechanism), and treat ML-based depth as an explicit v2 decision made after v1 is validated on-device — not a silent scope-creep item bolted onto the first release.

7 Risk register

HIGH
Spatial SDK panel orientation bug (upside-down load)

Recorded in Holoplex as intermittent and unresolved at the platform level, not tied to their specific screen graph. Validate on real Quest 3 hardware in a throwaway spike before committing engineering time to the full theater-mode build.

MED
Enter/exit transition feel

Handing off playback position, tracks, and decode state between the flat mpv surface and the Spatial panel's surface needs to be seamless (sub-second, no re-buffer) or the feature will feel broken even when the 3D itself works. Budget explicit spike time for this handoff before UI polish.

MED
Heuristic depth quality expectations

Community consensus (VisionDepth3D/IW3-class tools) is that live heuristic pseudo-depth looks like flat cutout layers, not real depth. Set that expectation explicitly in any release notes — "3D Auto" on ordinary 2D content is a comfort feature, not cinema-grade conversion.

LOW
Fire TV build divergence

None of this touches the Fire TV target — Spatial SDK and stereo panels are Horizon-only. Keep the new module strictly under a Quest-only build gate, same pattern as android/quest today.

LOW
Upstream rebase surface

A new Quest-only module and a new settings-sheet view are both new files/new enum cases — they don't touch any of the six upstream files QUEST_BUILD.md tracks as the fork's conflict surface, so this stays a clean addition rather than a modification.

8 Suggested phasing

Phase 0 — De-risk the platform bet 1-2 days

Throwaway Spatial SDK spike: register one ReadableVideoSurfacePanelRegistration panel, feed it a static SBS test pattern, confirm on a real Quest 3 that (a) it renders right-side-up reliably across multiple launches, and (b) exiting back to the flat 2D activity leaves the main app undisturbed. This is the single fact that determines whether Path B is buildable at all.

Phase 1 — Real-3D passthrough 1-2 weeks

Theater-mode Activity + handoff plumbing + stereoMode wired to source metadata/user override. Ships genuine stereo depth for any already-3D file in the library — the highest-value, lowest-risk slice, with zero synthetic depth involved.

Phase 2 — Heuristic 2D→3D + UI 3-5 days

Displacement GLSL shader with a strength uniform, the VideoSettingsSheet Mode/Strength view, and the repurposed player button, all landing on top of Phase 1's stereo panel.

Phase 3 — ML depth (optional follow-on) Separate multi-week project

Only after Phase 1-2 are validated on-device and the strength/UX model is proven out. Scope, model choice, and performance budget deserve their own dedicated design pass rather than riding along with the initial release.
